## Order of work

1. **Read `docs/cnlp-format.md`.** Nothing below makes sense before it, and it is the one
   file the migration keeps referring to.
2. **Run `/cnlp-migrate`** (Codex: `$cnlp-migrate`). Its first phase is an inventory: every
   top-level `key:` your existing skills already use, mapped onto blocks. That is what fills
   `custom_sections:` in `profiles/skill.md`. The profile is authored before any skill body is
   touched.
3. **Let it migrate a single skill end to end**, then read the diff before the rest follows.
4. **Prune `docs/cnlp-quality-rules.md`** and copy the variant a skill needs into its
   `quality_rules:` block, verbatim. Lines marked `[adr]` name artifacts you probably do not
   have.

## Running the check

```
node --test test/skill-format.test.js
```

It reads `SKILLS_DIR` at the top of that file, set to `.claude/skills`. If your skills live
somewhere else, move `.claude/skills/cnlp-migrate/` there and change that one line.

**No Node in this repository?** Delete `test/` and `tools/`, and set `enforcement:` in
`profiles/skill.md` to say the profile is held by review against the standard. The rest works
unchanged — the checker is a convenience, the standard is the authority. The checker has no
dependencies, so adding `node --test` later costs nothing but the files you deleted.

## What deliberately did not come along

- `transitions:` and `status_footer:` — lifecycle conventions of the project this came from.
  Add them to `profiles/skill.md` only if your skills have the same conventions.
- its 24 `custom_sections` names — that vocabulary is about architecture decision records,
  plans and review lenses. Yours comes from the inventory in step 2.
