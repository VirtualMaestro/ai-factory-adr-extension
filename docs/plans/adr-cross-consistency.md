# План: сквозная консистентность ADR

Статус: черновик для итерации, ревизия 2 (после внешнего ревью). Ничего не реализовано.
Итерируем по разделу «Открытые дыры» до закрытия, потом режем на задачи.

---

## 1. Контекст и мотивация

**Наблюдаемая проблема.** Новый ADR создаётся локально: агент решает задачу текущего файла,
проверяет код и те ADR, которые сам счёл связанными. Через несколько итераций проработки —
или уже на имплементации — выясняется, что решение противоречит другому, уже `accepted`
или `active` ADR.

**Причина не в дисциплине агента.** Обязанность проверять уже прописана, механизма нет:

- `skills/aif-adr-propose/SKILL.md` шаги 1–3: `ai-factory adr status --json`, затем
  «read the candidates that look related» — отбор кандидатов целиком на суждении агента.
- `skills/aif-adr-refine/SKILL.md` шаг 8: «record every conflict found with an active ADR» —
  как их найти, не сказано.

`ai-factory adr status` возвращает только id и статусы (`src/status.js:57`). Чтобы узнать,
**что** решает ADR, надо открыть файл целиком. Поэтому агент выбирает по догадке из заголовка
и промахивается.

**Настоящая причина: нет дешёвого представления того, что уже решено.**

**Что уже покрыто и чего не хватает.** Структурные связи между ADR проверяются:
`src/audit.js` (`audit-artifacts`) владеет дублями id, целями ссылок и циклами;
`src/status.js:36` предупреждает о зависимости на не-`active` или `superseded` ADR;
`src/order.js` строит порядок и находит циклы. Отсутствует ровно одно — **семантическая
проверка противоречий между решениями**. Всё ниже про неё.

**Почему это решаемо именно сейчас.** До CNL-P тело ADR было прозой — сжать его мог только
LLM. Сейчас `profiles/adr.md` объявляет `decision:` (scalar), `constraints:` (bullet-list),
`scope:` (bullet-list со строкой `excludes:`), `rules:` (numbered-list) обязательными
блоками, а `src/artifacts/cnlp.js` (`parseBlocks:28`, `readRecords:58`) их уже парсит.
Извлечение «что решено» становится детерминированным и бесплатным. Это не оплаченный до сих
пор дивиденд от миграции на CNL-P.

**Целевой результат.** Агент на `propose` и `refine` держит в контексте полный свод уже
принятых обязательств за постоянную малую цену, а полные чтения ADR остаются точечными.
Плюс отдельная проверка ADR↔ADR по требованию.

## 3. Рычаг 1 — `ai-factory adr rules` (дайджест решений)

### Что печатает

По каждому ADR в статусе `accepted` и `active`:

```text
adr-cnlp-single-format  [active]  affects: cnlp, skills
  decision: one CNL-P format for every document kind, no profile branching
  constraints: no per-kind branching in src/artifacts/cnlp.js
  scope: skill bodies, ADR bodies
    excludes: prose documents under docs/
  rules:
    1. every document body is CNL-P blocks
    2. what differs between kinds is declared in a profile, never branched in code
```

~7–10 строк на ADR. 50 ADR ≈ 400 строк ≈ 5k токенов — грузится целиком всегда.

### Контракт `buildDigest`

Новый `src/digest.js`:

```js
async function buildDigest({ projectDir = process.cwd(), statuses = ['accepted', 'active'] })
// → [{ id, status, affects: string[], decision: string,
//      constraints: string[], scope: string[], excludes: string[], rules: string[] }]
```

- **асинхронна** — `read` (`src/artifacts/frontmatter.js`) возвращает Promise;
- **сортировка по `id`**, лексикографическая. `listAdrs` (`src/status.js:9`) отдаёт порядок
  `readdir`, а он платформозависим; без сортировки вывод невоспроизводим;
- **источник статуса — каталог**, через `STATUS_BY_DIR` (`src/lifecycle/status.js`), как в
  `src/status.js:73`. Поле `status:` в YAML не читаем: расхождение каталога и поля ловит
  `validateAdr` (inv 4), дублировать проверку здесь нечего;
- **malformed ADR молча пропускается** — тот же контракт, что `src/status.js:29` и
  `src/order.js:74`; о них сообщают `status --check` и `audit-artifacts`;
- **дубли `id`** — предмет `src/audit.js`, не наш. Дайджест их не диагностирует, но и не
  падает: в вывод идут обе записи, различимые по статусу и порядку;
- **пустой блок** (ADR без `rules:`, например ещё не дописанный `accepted`) — пустой массив,
  не ошибка. `validate` уже делает это ошибкой на `accepted`/`active` (`validate.js:44-48`);
- **`excludes`** — не отдельный блок. По `profiles/adr.md:54` это элемент bullet-list `scope`,
  открывающийся словом `excludes:`. Алгоритм: снять маркер `- `, проверить префикс
  `excludes:`, остаток положить в `excludes[]`, элемент из `scope[]` исключить. Отсутствие
  такого элемента — пустой массив, не ошибка.

### Реализация

- переиспользует `listAdrs` (`src/status.js:9`), `STATUS_BY_DIR`, `read`
  (`src/artifacts/frontmatter.js`), `parseBlocks` (`src/artifacts/cnlp.js:28`);
- **требуется экспортировать `itemsOf`** из `src/artifacts/cnlp.js:48` (сейчас приватная) —
  одно слово, дублировать её нельзя;
- новый сабкоманд в `commands/adr.js` рядом с `order` (строка 192), тот же паттерн
  `out(opts, {...}, () => ...)` и `guard`;
- флаг `--json` — печатает массив записей как есть.

Объём: ~60 строк src + ~20 строк команды.

### Подключение к скиллам

- `aif-adr-propose`, workflow: после шага 1 — «run `ai-factory adr rules` and read it whole;
  open in full only the ADRs whose rules touch this topic»;
- `aif-adr-refine`, шаги 3 и 8: заземлить «detect conflicts with active ADRs» на дайджест —
  шаг 8 перестаёт быть беспредметным;
- вероятно `aif-adr-plan` (см. дыру №4).

**Ограничение при правке скиллов:** тела скиллов сами CNL-P и проверяются
`test/skill-format.test.js` + `test/skill-rubric.test.js`. Новые строки обязаны пройти лексикон:
без слов из `COMPARATIVE`/`DENY` (`src/artifacts/cnlp.js:10,17`), пороги цифрами, ≤250 символов.

## 4. Рычаг 2 — `aif-adr-check-consistency`

### Почему отбор пар — код, а не суждение

Наивная версия — попарное LLM-сравнение, O(n²): 50 ADR = 1225 пар, неприменимо, и ~95% пар
не связаны. Отбор кандидатов делает код, LLM работает только на выживших.

### `ai-factory adr overlaps`

Печатает пары-кандидаты с причинами. Отбор настроен **на полноту, не на точность**: дешёвая
лишняя пара стоит одного чтения выжимки, пропущенная пара стоит того самого конфликта, ради
которого всё затевается. Шум режет LLM на первой ступени.

Пара попадает в вывод, если выполнено хотя бы одно:

1. **пересечение `affects:`** — ≥1 общий элемент;
2. **пересечение `code:`** — общий путь после отсечения `#symbol`. Отсекать так же, как
   `src/lifecycle/verify.js:36` (`indexOf('#')`), разделители нормализовать к `/`;
3. **лексическое пересечение** — общие нормализованные токены в `scope:` + `rules:`
   (нижний регистр, стоп-слова выброшены, порог: ≥2 общих токена).

Признак 3 обязателен, потому что первые два дырявы: `code:` на `accepted` не проверяется
вообще, а на `active` пустой список даёт лишь warning (`src/lifecycle/validate.js:76-79`);
`affects:` необязателен и на практике пуст (дыра №1). Без третьего признака два `accepted`
ADR не пересекутся ни по чему. Блоки `scope:`/`rules:` обязательны по профилю — значит
признак 3 есть всегда.

Правила по `supersedes` **нет**: `src/lifecycle/supersede.js:16` уводит старый ADR в
`superseded/`, а корпус — `accepted` + `active`, поэтому в паре остаётся только новый.
Существующее ребро `depends_on` между двумя ADR корпуса даёт метку `linked`, но пару не
выбрасывает: связь могла устареть.

**Детерминированность вывода:** пара канонизируется (лексикографически меньший `id` первым),
пары дедуплицируются, причины перечисляются в фиксированном порядке `affects`, `code`,
`lexical`, список пар сортируется по первому `id`, затем по второму.

Флаг `--check`: ненулевой код выхода, если есть пара с пересечением по признакам 1 или 2 и
без объявленной связи. Это детерминированный факт, годный для CI. Признак 3 в гейт не входит
— он приблизительный.

Реализация: ~50 строк в `src/consistency.js` поверх тех же данных, что дайджест.

### Скилл

`skills/aif-adr-check-consistency/SKILL.md`, форма один-в-один как `aif-adr-verify-all`
(read-only, одна таблица, follow-up скиллы).

Вход: нет, скилл сам находит корпус.

**Две ступени чтения** — это ядро экономики скилла:

1. **отсев по выжимке.** `adr rules` + `adr overlaps`; по каждой паре сравнить
   `decision` + `scope`/`excludes` + `rules` + `constraints`. Пары, где пересечения по сути
   нет, закрываются здесь и в отчёт не идут;
2. **полное чтение.** Оба документа целиком — только для переживших ступень 1. Вердикт
   `contradiction` разрешено выдавать **только** после полного чтения обоих: выжимка не
   содержит `constraints` в контексте, `out_of_scope`, `alternatives.rejected_because` и
   оснований, а без них противоречие легко померещится.

Вердикты:

- `contradiction` — правила или scope пары несовместимы;
- `overlap-unlinked` — оба правят одну область, объявленной связи нет;
- `redundant` — `rules:` одного целиком покрыты другим.

Follow-up:

- `contradiction` → `aif-adr-refine` (если оба ещё `accepted`) или `aif-adr-supersede`
  (если один `active`, PRD §18.3);
- `overlap-unlinked` → `aif-adr-refine`: уточнить `scope:` и строку `excludes:` так, чтобы
  границы перестали накладываться. **`depends_on` не рекомендовать**: это отношение порядка
  реализации (`src/order.js:55-64`), `next` требует все зависимости `active`, а лишние рёбра
  дают ложные блокировки и циклы с ненулевым кодом выхода `adr order`. Ребро ставится только
  когда реализация действительно требует порядка, и это решает оператор;
- `redundant` → `aif-adr-supersede`, где замещается тот ADR, чьи `rules:` покрыты целиком;
  при взаимном покрытии follow-up нет, решает оператор (`supersede` требует явной пары
  старый/новый, `src/lifecycle/supersede.js:16`).

Запрещено: править ADR, править код, менять статус.

### Каденция

Дайджест — профилактика, на каждом propose/refine. Этот скилл — обнаружение, по требованию:
после `aif-adr-migrate`, перед релизом, изредка. Автозапуска нет.

## 6. Открытые дыры — итерируем здесь

### Решено в этой ревизии

1. **Гейт на `accept`.** Отклонён. Вердикт LLM в коде выхода ломает разделение «CLI владеет
   механикой, скиллы владеют суждением» (`skills/aif-adr-overview/SKILL.md`,
   `rules_that_always_hold`) и делает приёмку невоспроизводимой. Замена: `adr overlaps --check`
   — детерминированный факт, годен для CI.
2. **Надёжность вердикта против цены.** Решено двумя ступенями чтения (§4): полные документы
   читаются только для подозрительных пар, `contradiction` — только после них.
3. **Признак отбора, доступный всегда.** Решено лексическим признаком 3 (§4).

### Открыто

1. **Словарь `affects:` — блокирующая.** Сейчас свободный текст, никто не заполняет и не
   валидирует. Признак 1 держится на нём, а `--check` без него почти всегда пуст. Что
   считается легальным элементом — путь модуля? имя домена? Кто проверяет — `validate`?
   Требовать непустой `affects:` на `accept`? *Без ответа Рычаг 2 работает на признаке 3,
   то есть приблизительно, а гейт `--check` бесполезен.*
2. **Дайджест видит только то, что автор выписал в блоки.** Конфликт вида «ADR-7
   предполагает синхронный поток, ADR-22 делает его асинхронным» невидим, если он не выписан
   ни в `decision:`, ни в `rules:`, ни в `constraints:`. Дайджест давит на качество этих
   блоков — принимаем как цену или добавляем что-то в выжимку?
3. **Статусы.** Дайджест — `accepted` + `active`, по §23 верно. Но check-consistency, может,
   должен смотреть шире: `superseded` (новый ADR воскрешает отвергнутый вариант — сравнение
   пошло бы по `alternatives.rejected_because`), `draft` (два черновика в полёте конфликтуют
   между собой).
4. **Где ещё грузить дайджест.** `aif-adr-plan` и `aif-adr-implement` — да или нет? Решение
   там уже принято, но план всё равно может нарушить чужое правило.
5. **Потолок объёма.** Длинные `rules:` раздувают дайджест. Резать по N строк на ADR? Молча
   резать нельзя — агент не узнает, что видит не всё.
6. **Порог лексического признака.** «≥2 общих токена» взято с потолка. Настраивается только
   на реальном корпусе; до первого прогона это заглушка.
7. **Масштабирование.** Фильтр `--affects <term>` откладываем; триггер на добавление —
   дайджест превышает ~500 строк.
8. **Именование.** `adr rules` / `adr digest` / `adr decisions`. `rules` короче и совпадает с
   именем блока; риск спутать с `.ai-factory/RULES.md`.

## 8. Критерий успеха

Работа считается сделанной, когда на реальном корпусе этого репозитория:

1. `adr rules` укладывается в 500 строк и печатает непустые `decision` и `rules` для каждого
   `accepted`/`active` ADR;
2. `adr overlaps` возвращает не более ~20% всех возможных пар — иначе отбор не отбирает и
   вторая ступень скилла разорительна;
3. на паре, конфликт которой известен заранее, скилл даёт `contradiction` и цитирует оба
   правила; на паре заведомо несвязанных ADR — молчит;
4. `propose` и `refine` после правки не тратят на дайджест больше, чем одно чтение среднего
   ADR-файла.

Пункты 2 и 3 меряются один раз, вручную, на первом прогоне. Автоматизировать их незачем.

## Приложение: что из ревью отклонено

- **«Скилл обязан читать оба документа целиком для каждой пары».** Отклонено в этом виде:
  возвращает O(n²) полных чтений, то есть ровно ту цену, ради устранения которой всё
  затевается. Взято по существу — полное чтение обязательно, но только на второй ступени и
  только для подозрительных пар (§4).
- **«Гейт на `accept`, иначе проверка остаётся необязательной ручной».** Отклонено:
  недетерминированный вердикт в коде выхода ломает архитектурное разделение и
  воспроизводимость приёмки. Заменено на `adr overlaps --check` (§6, решение 1).
- **«Детерминированность не обеспечена».** Принято как уточнение контракта (сортировка,
  канонизация, дедуп — §3, §4), но не как опровержение: в плане слово означало «отбор пар
  делает код, а не суждение LLM». Теперь в тексте оба смысла названы явно.

Остальные 11 пунктов ревью приняты целиком и разнесены по §3, §4, §5, §6, §7.
