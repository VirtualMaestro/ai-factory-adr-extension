# План: сквозная консистентность ADR

Статус: ревизия 7. Шаги 1–2 §9 в работе; §7 держит принятые решения и потолки.

---

## 1. Контекст и мотивация

**Наблюдаемая проблема.** Новый ADR создаётся локально: агент решает задачу текущего файла,
проверяет код и те ADR, которые сам счёл связанными. Через несколько итераций проработки —
или уже на имплементации — выясняется, что решение противоречит другому, уже `accepted`
или `active` ADR.

**Причина не в дисциплине агента.** Обязанность проверять уже прописана, механизма нет:

- `skills/aif-adr-propose/SKILL.md` шаги 1–3: `ai-factory adr status --json`, затем
  «read the candidates that look related» — отбор кандидатов целиком на суждении агента;
- `skills/aif-adr-refine/SKILL.md` шаг 8: «record every conflict found with an active ADR» —
  как их найти, не сказано;
- `skills/aif-adr-accept/SKILL.md` precondition 24: «conflicts with active ADRs are resolved
  or explicitly addressed» — предусловие приёмки, проверить которое нечем.

`ai-factory adr status` возвращает только id и статусы (`src/status.js:57`). Чтобы узнать,
**что** решает ADR, надо открыть файл целиком. Поэтому агент выбирает по догадке из заголовка
и промахивается.

**Настоящая причина: нет дешёвого представления того, что уже решено.**

**Что уже покрыто и чего не хватает.** Структурные связи между ADR проверяются:
`src/audit.js` (`audit-artifacts`) владеет дублями id, целями ссылок и циклами;
`src/status.js:36` предупреждает о зависимости на не-`active` или `superseded` ADR;
`src/order.js` строит порядок и находит циклы. Отсутствует ровно одно — **семантическая
проверка противоречий между решениями**. Всё ниже про неё.

**Почему это решаемо именно сейчас.** До CNL-P тело ADR было прозой — сжать его мог только
LLM. Сейчас `profiles/adr.md` объявляет `decision:` (scalar), `constraints:` (bullet-list),
`scope:` (bullet-list со строкой `excludes:`), `rules:` (numbered-list) обязательными
блоками, а `src/artifacts/cnlp.js` (`parseBlocks:28`, `readRecords:58`) их уже парсит.
Извлечение «что решено» становится детерминированным и бесплатным. Это не оплаченный до сих
пор дивиденд от миграции на CNL-P.

**Целевой результат.** Агент на `propose`, `refine`, `plan` и `accept` держит в контексте
полный свод уже принятых обязательств за постоянную малую цену, а полные чтения ADR остаются
точечными.

## 2. Форма решения

Одна команда и один скилл поверх неё:

- `ai-factory adr decisions` — детерминированная выжимка корпуса, ~8 строк на ADR;
- `aif-adr-check-consistency` — читает выжимку целиком **одним проходом** и называет
  подозрительные пары сам, затем открывает подозрительные ADR полностью.

Второй CLI для отбора пар не нужен: 50 ADR ≈ 5k токенов, это один проход, а не O(n²) вызовов.
Эвристический предфильтр (лексическое пересечение, пороги, стоп-слова) выброшен — см. §8.

Не делаем:

- семантический индекс, эмбеддинги, слой памяти — решено 2026-07-14 (Cognee отброшен,
  `docs/BACKLOG.md` §«Decided»); выжимка бесплатна, сервис нет;
- автозапуск проверки на каждом `propose` — это сжигание ресурсов, которого мы избегаем;
- гейт по вердикту LLM в коде выхода — §8;
- любые правки ADR автоматикой: и команда, и скилл read-only.

## 3. `ai-factory adr decisions`

### Что печатает

По каждому ADR в статусе `accepted` и `active`:

```text
adr-cnlp-single-format  [active]  docs/adr/active/adr-cnlp-single-format.md
  decision: one CNL-P format for every document kind, no profile branching
  constraints: no per-kind branching in src/artifacts/cnlp.js
  scope: skill bodies, ADR bodies
    excludes: prose documents under docs/
  rules:
    1. every document body is CNL-P blocks
    2. what differs between kinds is declared in a profile, never branched in code
  affects: cnlp, skills · depends_on: adr-cnlp-profiles · code: src/artifacts/cnlp.js#parseBlocks
```

Последней строкой всего вывода — итог: `42 ADR · 371 lines`. Он нужен для потолка §7,
решение 2.

~8–11 строк на ADR. 50 ADR ≈ 450 строк ≈ 5–6k токенов — грузится целиком.

**Путь к файлу стоит в строке заголовка.** Скилл открывает выбранные ADR на второй ступени, а
при кастомном `adr.root` из `.ai-factory/adr-extension.yaml` путь по `id` не угадывается.
Заставлять скилл ради этого читать многословный `--json` — дороже одного столбца.

`affects:`, `depends_on:` и `code:` печатаются только непустыми, одной строкой.

`code:` печатается **как написано автором, вместе с `#symbol`**: это подсказка модели, куда
смотреть на второй ступени. Отсечение символа было нужно машинному сопоставлению путей, а
машинного сопоставления больше нет (§8).

`depends_on:` печатается **как контекст, не как индульгенция**: объявленный порядок
реализации ничего не говорит о смысловой совместимости решений. Два ADR со связью
`depends_on` противоречат друг другу ровно так же легко, как два несвязанных.

### Контракт

Новый `src/decisions.js`. Один загрузчик корпуса, две проекции — команда и скилл берут одно
и то же:

```js
const STATUSES = ['accepted', 'active']; // §7, решение 1

async function buildDecisions({ projectDir = process.cwd() })
// → { items: [{ id, status, file, affects, decision, constraints,
//               scope, excludes, rules, depends_on, code }],
//     issues: [{ code, file, message }] }
```

- **асинхронна** — `read` (`src/artifacts/frontmatter.js`) возвращает Promise;
- **корень ADR резолвится первым**: `await adrRoot(projectDir)`, затем `listAdrs(root)` —
  `listAdrs` (`src/status.js:9`) принимает корень ADR, не корень проекта. Паттерн буквально
  как в `buildStatus` (`src/status.js:58`). Тест на кастомный `adr.root` обязателен;
- **набор статусов захардкожен**. Параметризовать его было бы гибкостью ради одного теста, а
  фильтрацию по статусам проверяют реальные каталоги фикстуры. Второй потребитель появится —
  тогда и параметр;
- **`items` сортируются по `(id, file)`**. `listAdrs` отдаёт порядок `readdir`,
  платформозависимый; сортировки по одному `id` мало — при дубле `id` порядок двух записей
  остался бы неопределённым;
- **`file`** — путь относительно `projectDir`, обязателен: без него дубли `id` неразличимы, и
  скиллу нечего открывать;
- **источник статуса — каталог**, через `STATUS_BY_DIR` (`src/lifecycle/status.js`), как в
  `src/status.js:73`;
- **`code`, `affects`, `depends_on`**: скаляр приводится к массиву из одного элемента, как
  `src/status.js:37-39` делает с `depends_on`. Отсутствие — пустой массив. Новых классов
  ошибок для этого не заводим: поведение совпадает с уже существующим в проекте;
- **код выхода при `issues` — ноль.** `issues` это диагностика, а не отказ: матрица §3
  требует, чтобы `propose` и `refine` продолжали работу на неполном своде, и ненулевой код
  ломал бы её. Ненулевой код только когда команда не выполнилась целиком — это уже делает
  `guard` (`commands/adr.js:252`). Флага `--check` у команды нет.

### Что попадает в `issues`

`issues` — тот же по смыслу канал, что `report.issues` в `buildStatus` (`src/status.js:67`),
но записями, а не строками: скиллам нужен файл и код, чтобы решить, останавливаться ли им
(§7, решение 5). Молчаливый пропуск здесь опаснее, чем где-либо: выжимка заявляет себя
полным сводом обязательств, и дыра в ней даёт ложную уверенность.

| `code` | Когда | Источник |
|---|---|---|
| `unreadable` | `read` бросил: битый YAML, нечитаемый файл | try/catch вокруг `read` |
| `invalid-id` | `id` отсутствует или не проходит `isValidId` | `src/artifacts/id.js` |
| `duplicate-id` | тот же `id` уже встречен в целевых статусах | набор увиденных id |
| `status-mismatch` | `data.status` ≠ `STATUS_BY_DIR[dir]` | сравнение, inv 4 |
| `empty-block` | пустой `decision`, `constraints`, `scope` или `rules` | собственное извлечение |
| `invalid-block` | обязательный блок объявлен больше 1 раза | собственное извлечение |

`duplicate-id` выдаётся **отдельной записью на каждый из конфликтующих файлов**, с одинаковым
`message`, называющим оба пути. Иначе поле `file` пришлось бы делать массивом ради одного
кода, а счёт «M ADR» в отчёте скилла перестал бы сходиться.

`invalid-block` закрывает тихую потерю содержания: два блока `rules:` в одном теле — выжимка
возьмёт первый и промолчит, `empty-block` при этом не сработает. Определяется из того же
списка секций, который extractor уже держит: ключ обязательного блока встретился больше
одного раза.

**Ни `validateAdr`, ни `bodyIssues` здесь не переиспользуются.** `validateAdr` тянет
`resolveActivePlan` и `resolvePlans` на каждый `accepted`/`active` ADR (`validate.js:53-63`) —
обход каталога планов на каждый файл корпуса — плюс диагностику связи ADR↔план, чуждую своду
обязательств. `bodyIssues` (`cnlp.js:152`) на первый взгляд подходит, но на строке 222
дописывает к результату `lexiconIssues`: неквантифицированные сравнения, пороги словами,
250 символов. Это стилевые претензии к формулировкам, они принадлежат `adr validate` и
`aif-adr-refine`, а в своде обязательств были бы шумом, из-за которого `accept` и
`check-consistency` останавливались бы на ровном месте. Шесть кодов выше берутся из данных,
которые загрузчик и так держит в руках, и стоят несколько строк.

### Реализация

- переиспользует `adrRoot` (`src/config/paths.js`), `listAdrs` (`src/status.js:9`),
  `STATUS_BY_DIR`, `read` (`src/artifacts/frontmatter.js`), `isValidId`
  (`src/artifacts/id.js`), `parseBlocks` (`src/artifacts/cnlp.js:28`);
- **требуется экспортировать `itemsOf`** из `src/artifacts/cnlp.js:48` (сейчас приватная) —
  одно слово, дублировать её нельзя;
- **`excludes`** — не отдельный блок. По `profiles/adr.md:54` это элемент bullet-list `scope`,
  открывающийся словом `excludes:`. Алгоритм: снять маркер `- `, проверить префикс
  `excludes:`, остаток положить в `excludes[]`, элемент из `scope[]` исключить. Отсутствие —
  пустой массив, не ошибка: профиль его не требует;
- новый сабкоманд в `commands/adr.js` рядом с `order` (строка 192), тот же паттерн
  `out(opts, {...}, () => ...)` и `guard`;
- `--json` печатает `{ command: 'decisions', items, issues }` — соглашение вывода из
  `commands/adr.js:25`, а не голый массив;
- `issues` в человекочитаемом режиме идут в `stderr`, как `report.issues` в `status`
  (`commands/adr.js:186`), строкой `<code>  <file>: <message>`.

Объём: ~80 строк src + ~25 строк команды.

### Подключение к скиллам

Четыре точки, по одной строке в каждой:

| Скилл | Куда | Зачем |
|---|---|---|
| `aif-adr-propose` | после шага 1 | не создать решение, противоречащее принятому |
| `aif-adr-refine` | шаги 3 и 8 | заземлить «detect conflicts with active ADRs» |
| `aif-adr-plan` | шаг 1 | план не меняет решение, но нарушить чужое правило может |
| `aif-adr-accept` | новый шаг перед `transition` | это момент, где документ становится правилом |

Формулировка везде одна: прочитать вывод `ai-factory adr decisions` целиком, открывать
полностью только те ADR, чьи правила касаются темы.

`aif-adr-accept` — самая важная из четырёх: его precondition 24 сегодня ничем не обеспечен,
и именно там закрывается конфликт двух черновиков (§7, решение 1).

**Реакция на `issues`** (§7, решение 5):

| Скилл | Issue на целевом ADR | Issue на любом другом |
|---|---|---|
| `aif-adr-propose` | — (своего ADR ещё нет) | назвать и продолжить |
| `aif-adr-refine` | назвать и продолжить: refine и чинит такое | назвать и продолжить |
| `aif-adr-plan` | **остановиться**: планировать по битому решению нечего | назвать и продолжить |
| `aif-adr-accept` | уже покрыт своим шагом 2 | уже покрыт своим шагом 2 |
| `aif-adr-check-consistency` | — | **остановиться** |

Формулировка отчёта: «N проблем в M ADR», перечислением `code` и `file`. Прежняя строка
«N ADR не прочитаны» неверна: при `empty-block` и `duplicate-id` файлы прочитаны.
Учитываются только `issues` из `accepted`/`active` — битый файл в `proposals/` свод
обязательств не портит.

**Своего стоп-правила `aif-adr-accept` не получает.** Его шаг 2 уже запускает
`ai-factory adr status --check`, `buildStatus` собирает ошибки `validateAdr` по всему корпусу,
и `--check` даёт ненулевой код (`commands/adr.js:189`), а шаг 3 требует их разрешить.
`invalid-id`, `status-mismatch` и `empty-block` на `accepted`/`active` — это ровно ошибки
`validateAdr`, `duplicate-id` ловит `audit-artifacts`. Второе правило о том же было бы
дублем. Ценность подключения к `accept` — в чтении свода, а не в остановке.

**Кому вообще адресованы `issues`.** На проекте, где `adr status --check` зелёный, они пусты
почти всегда — по той же причине. Их настоящий адресат — корпус в середине
`aif-adr-migrate`, где часть ADR ещё не приведена к профилю, и `check-consistency`, которому
дырявый свод противопоказан.

**Ограничение при правке скиллов:** тела скиллов сами CNL-P и проверяются
`test/skill-format.test.js` + `test/skill-rubric.test.js`. Новые строки обязаны пройти лексикон:
без слов из `COMPARATIVE`/`DENY` (`src/artifacts/cnlp.js:10,17`), пороги цифрами, ≤250 символов.

## 4. `aif-adr-check-consistency`

`skills/aif-adr-check-consistency/SKILL.md`, форма один-в-один как `aif-adr-verify-all`
(read-only, одна таблица, follow-up скиллы). Вход: нет, скилл сам находит корпус.

### Форма файла

Тело подчиняется `profiles/skill.md` и проверяется `test/skill-format.test.js`, где любое
несоответствие — ошибка, а не предупреждение. Обязательны `mode`, `purpose`, `inputs`,
`workflow`, `invocation`. Сверх того нужны:

- `targeting_rationale` — почему корпус это `accepted` + `active`, по образцу
  `aif-adr-verify-all`, где тем же блоком объясняется выбор только `active`;
- `verdicts` и `follow_up` — содержание ниже;
- `report_format` — таблица `| Пара | Вердикт | Основание |`, в `text`-фенсе, как у
  `aif-adr-verify-all`;
- `status_footer` — `format` и `source`, как у всех скиллов семейства;
- `quality_rules` — группа `SHORT` теста `test/skill-rubric.test.js`, текст посимвольно
  совпадает с `aif-adr-verify-all`.

Все четыре нестандартных ключа (`targeting_rationale`, `verdicts`, `follow_up`,
`report_format`) уже перечислены в `custom_sections` профиля — новых имён вводить не нужно.
Формулировки проходят лексикон: без слов из `COMPARATIVE`/`DENY`, пороги цифрами.

### Две ступени

1. **Один проход по выжимке.** `ai-factory adr decisions`, прочитать целиком, назвать пары,
   у которых `decision`/`constraints`/`scope`/`rules` выглядят пересекающимися. Отбор — работа
   самой модели, а не кода: пересечение синонимично («сессия» против «токен доступа»), и
   никакой лексический фильтр этого не увидит. Один проход стоит один раз, независимо от
   числа пар.
2. **Полное чтение.** Оба документа целиком — для каждой названной пары. **Любой финальный
   вердикт выдаётся только после этого**: выжимка не содержит `out_of_scope`,
   `alternatives.rejected_because` и оснований, а без них и противоречие мерещится, и
   избыточность.

Корпус — `accepted` + `active`. `superseded` в v1 не рассматривается вовсе: сценарий
«новый ADR воскрешает отвергнутый вариант» требует индекса цепочек `supersedes`/`replaced_by`,
которого в выжимке нет, и он остаётся за рамками (§7, решение 6).

### Вердикты

- `contradiction` — обязательства, вытекающие из `decision`, `constraints`, `scope` или
  `rules` пары, невозможно выполнить одновременно. Формулировка совпадает с тем, что скилл
  сравнивает на первой ступени: сузить вердикт до `rules` и `scope` значило бы объявить
  безобидными конфликты, живущие в самом решении или в его ограничениях;
- `redundant` — один ADR целиком покрыт другим по `decision` **и** `constraints` **и**
  `scope` **и** `rules`. Совпадения одних `rules:` мало: те же правила при разных `scope`
  избыточностью не являются;
- `shared-area` — оба правят одну область, противоречия нет. **Информационный, не дефект.**

### Follow-up

`contradiction`, по статусам пары:

| Пара | Действие |
|---|---|
| `accepted` + `active` | `aif-adr-refine` на `accepted`: он ещё не реализован, переписать его дешевле, а `active` защищён PRD §18.3 |
| `accepted` + `accepted` | назвать конфликт и остановиться: оба переписываемы, какой из них уступает — выбор оператора, и он может решить править оба |
| `active` + `active` | назвать конфликт и остановиться: оба реализованы и защищены, направление замены из самого конфликта не следует |

`aif-adr-supersede` вызывается только **после** операторского выбора, явной парой
старый/новый (`src/lifecycle/supersede.js:16`), и скиллом не предлагается.

`redundant` → назвать перекрытие и остановиться: из покрытия пара старый/новый тоже не следует.

`shared-area` → ничего. Строка в отчёте, чтобы автор знал о соседе.

**`depends_on` не рекомендуется никогда.** Это отношение порядка реализации
(`src/order.js:55-64`): `next` требует все зависимости `active`, лишние рёбра дают ложные
блокировки и циклы с ненулевым кодом выхода `adr order`. Ребро ставит оператор, когда
реализация действительно требует порядка.

Запрещено: править ADR, править код, менять статус.

### Каденция

Выжимка — профилактика, на каждом propose/refine/plan/accept. Скилл — обнаружение, по
требованию: после `aif-adr-migrate`, перед релизом, изредка. Автозапуска нет.

## 6. Тестовые корпуса

В этом репозитории нет ни `docs/adr`, ни `.ai-factory` — «реального корпуса» здесь не
существует, и мерить на нём нечего. Корпусов нужно два, потому что один самоблокируется:
скилл обязан остановиться при `issues`, а значит корпус с подсаженными дефектами не годится
для замера recall. Строятся они **по-разному**, и это не небрежность.

**Грязный корпус — кода, не файлов.** Каталогов `test/fixtures/` в проекте не существует:
все тесты собирают временный проект через `mkProject()` + `writeAdr()` (`test/helpers.js:9,63`),
причём `writeAdr` уже пишет тело, conformant с `profiles/adr.md`. Шесть кодов `issues`
проверяются тем же приёмом — `writeAdr` с намеренно битым телом или frontmatter. Заводить
ради них каталог в репозитории значило бы вводить второй приём там, где первый покрывает всё.

**Чистый корпус — checked-in, `test/fixtures/consistency-corpus/`.** Он единственный, кому
нужна долговечность: по нему идёт **ручной** прогон скилла три раза подряд, а человек
перечитывает разметку и сверяет вердикты. Временный каталог, исчезающий после теста, для
этого не годится. Это первая фикстура-каталог в проекте — заводится сознательно и только
под этот сценарий.

12–14 ADR в `accepted/` и `active/`, разметка в `expected.json`:

- 3 пары с настоящим противоречием — по одной на каждую ветку follow-up §4:
  `accepted`+`active`, `accepted`+`accepted`, `active`+`active`;
- одна из трёх выражена синонимами, а не общими словами;
- 1 пара избыточных;
- 2 пары, делящих область без конфликта (ловушка на ложный `contradiction`);
- остальные ортогональны.

Грязный корпус собирается в `test/decisions.test.js` по одному временному проекту на код:
битый YAML (`unreadable`), `id` не проходит `isValidId` (`invalid-id`), два файла с одним `id`
(`duplicate-id`, две записи в `issues`), поле `status` против каталога (`status-mismatch`),
пустой `rules:` у `accepted` (`empty-block`), два блока `constraints:` в одном теле
(`invalid-block`).

## 7. Закрытые вопросы

**1. Статусы выжимки: только `accepted` + `active`.** По §23 (`aif-adr-overview`,
`rules_that_always_hold`) черновик правилом не является, и подмешивать его в свод нельзя:
агент, читающий выжимку, обязан считать каждую её строку действующим обязательством.

Конфликт двух черновиков в полёте закрывается не расширением выжимки, а точкой подключения:
`aif-adr-accept` читает свод перед `transition`. Первый черновик, принятый раньше, к моменту
приёмки второго уже в `accepted` и уже в выжимке. Дыра закрывается порядком приёмки, без
нового механизма.

**2. Потолок объёма: назван, не построен.** Команда печатает итоговую строку
`N ADR · M lines`. Порог — 800 строк: за ним один проход перестаёт быть дешёвым. Что делать
тогда: срез по `code:`/`affects:` относительно текущей задачи. Пока корпус меньше — фильтра
нет, потому что фильтр без корпуса не настроить, а неверный фильтр молча прячет решения.
Отметить в коде `// ponytail: whole corpus per read; slice by affects/code past ~800 lines`.

**3. Выжимка видит только выписанное — принимаем как цену, но давим на источник.** Конфликт
«ADR-7 предполагает синхронный поток, ADR-22 делает его асинхронным» невидим, если он не
выписан ни в `decision:`, ни в `rules:`, ни в `constraints:`. Правильное место лечения —
авторство: в `aif-adr-refine` добавляется строка «обязательство, которое другой ADR мог бы
нарушить, пишется в `rules:` или `constraints:`, а не в прозу `## Context`». Остаточный риск:
правило не выписано **и** пара не попала в кандидаты. Это потолок подхода, а не дефект
реализации.

**4. `affects:` остаётся в выводе, словаря не получает.** Отбор пар больше на нём не стоит,
так что блокирующим он быть перестал. Печатаем непустым — модели это дешёвая подсказка о
соседстве, и это же будущий срез для потолка решения 2. Валидацию и словарь не вводим: host
audit уже нудит «Accepted ADR without `affects` links» (`aif-adr-plan`, `expected_warnings`),
второго давления на то же поле не нужно.

**5. `issues`: авторство продолжается с названной дырой, аудит останавливается.**
Матрица в §3. `plan` останавливается на `issues` **своего** ADR — планировать по битому
решению нечего, — но на чужих только предупреждает. `accept` своего правила не получает: его
шаг 2 уже блокирует приёмку на тех же ошибках через `adr status --check`.

**6. Исторический сценарий вынесен из v1.** Проверка «новое решение возвращает отвергнутый
ранее вариант» требует индекса цепочек `supersedes`/`replaced_by`, а выжимка этих полей не
несёт и нести не должна: она про действующие обязательства. Добавлять поле в вывод ради
сценария, которого пока никто не просил, — спекуляция.

## 8. История ревизий

**Ревизия 3 → 4.** Предфильтр пар удалён: выжимка целиком влезает в один LLM-проход, а
лексическое пересечение не ловит синонимы и требует порогов, которых никто не измерял.
Удалены команда `adr overlaps`, лексический признак, флаг `--check` как CI-гейт (общий
`affects:` или общий файл конфликтом не являются — ортогональные решения одного модуля
роняли бы сборку). `overlap-unlinked` → `shared-area` без follow-up: прежний вердикт толкал
автора сузить правдивый `scope:`, лишь бы погасить предупреждение. Контракт расширен до
`file`, `code`, `depends_on`, `issues`. JSON приведён к `{command, ...}`.

**Ревизия 4 → 5.** `adrRoot` перед `listAdrs` — пропущенный шаг, `listAdrs` принимает корень
ADR, не проекта. Сортировка по `(id, file)`. `issues` стали записями `{code, file, message}`.
Фикстура разделена на две — прежняя блокировала собственный замер recall. `depends_on` в
выводе понижен до контекста. Нормализация `code:` отменена, `#symbol` восстановлен — она была
нужна машинному сопоставлению путей, умершему вместе с `overlaps`. Follow-up для
`contradiction` разведён по статусам пары. Исторический сценарий по `replaced_by` вынесен из v1.

**Ревизия 5 → 6.** `duplicate-id` — отдельная запись на каждый конфликтующий файл, иначе
`file` пришлось бы делать массивом ради одного кода. Добавлен `invalid-block`: два блока
`rules:` в теле дают тихо усечённую выжимку, и `empty-block` этого не ловит. Код выхода при
`issues` зафиксирован нулевым — иначе матрица реакций, где `propose` и `refine` продолжают
работу, неисполнима. Путь к файлу вынесен в строку заголовка: скилл открывает ADR на второй
ступени, а при кастомном `adr.root` путь по `id` не угадывается. Определение `contradiction`
расширено до четырёх блоков — ровно тех, что скилл сравнивает. Добавлена ветка
`accepted`+`accepted` и третья конфликтная пара в фикстуру. Параметр `statuses` убран:
гибкость ради одного теста. Добавлен статический тест подключения скиллов (§10).

**Ревизия 6 → 7** (собственный аудит плана против репозитория). Грязный корпус переведён с
каталога-фикстуры на `mkProject`/`writeAdr` — каталогов `test/fixtures/` в проекте нет, и
существующий приём покрывает задачу целиком; checked-in остаётся только чистый корпус, ради
ручного прогона. Добавлена «Форма файла» в §4: `profiles/skill.md` требует `mode`, `purpose`,
`inputs`, `workflow`, `invocation`, а `status_footer`, `report_format` и
`targeting_rationale` план прежде не называл. Стоп-правило `aif-adr-accept` удалено как дубль
его же шага 2. Названа версия релиза. PRD не трогаем: он существует
(`docs/archive/ai-factory-adr-extension-PRD.md`), но пять пост-MVP скиллов — `verify`,
`verify-all`, `next`, `migrate`, `plan-improve` — собственных PRD-якорей не имеют, и новые
артефакты следуют этому прецеденту.

**Отклонено.** «Переиспользовать `validateAdr`» и «переиспользовать `bodyIssues`» — оба с
обоснованием в §3: первая тянет обход каталога планов на каждый ADR, вторая на `cnlp.js:222`
подмешивает `lexiconIssues`, то есть стилевые претензии к формулировкам, из-за которых
`accept` и `check-consistency` останавливались бы на ровном месте. Взята сама претензия —
неоднозначный блок теперь ловится кодом `invalid-block` из собственного извлечения.
«3 из 3 прогонов на каждом поддерживаемом рантайме» — сужено до 3 прогонов на одном плюс
один дымовой на втором, §10.

  `invalid-id`, `duplicate-id` (две записи, оба пути в `message`), `status-mismatch`,
  `empty-block`, `invalid-block`. Обход не падает ни на одном;
- `test/skill-wiring.test.js` — новый, статический: четыре скилла §3 содержат вызов
  `ai-factory adr decisions`; `aif-adr-accept` и `aif-adr-check-consistency` содержат правило
  остановки при `issues`. Ни `skill-format`, ни `skill-rubric` этого не проверяют, а подключение
  и есть весь смысл шага 2 — оно должно ломаться заметно;
- `test/integration/extension-lifecycle.test.js`: один реальный вызов
  `ai-factory adr decisions --json` в развёрнутом проекте — доказательство, что команда
  зарегистрирована и работает через host CLI, а не только как модуль;
- `test/skill-format.test.js`, `test/skill-rubric.test.js`, `test/extension-manifest.test.js` —
  зелёные после правки скиллов и счётчиков.

**Критерий успеха скилла** — на чистой фикстуре, вручную:

1. **recall размеченных конфликтов = 100%**, включая пару, выраженную синонимами. Первичная
   метрика: пропущенный конфликт и есть та боль, ради которой всё делается;
2. ни одна из двух ловушек `shared-area` не получает вердикт `contradiction`;
3. follow-up соответствует статусам пары во всех трёх ветках §4;
4. `adr decisions` на фикстуре укладывается в 180 строк, а на корпусе в 50 ADR — в 500.

**Воспроизводимость.** Один прогон LLM ничего не доказывает. Критерий 1 засчитывается при
**3 успешных прогонах из 3** на том рантайме, где скилл разрабатывается, плюс **1 дымовой
прогон** на втором поддерживаемом рантайме — расхождение между рантаймами это уже другой
вопрос, и гонять по три прогона на каждом ради него дорого. Разброс вердиктов между
прогонами записывается в отчёт: он и есть мера того, насколько формулировкам скилла можно
верить.

Доля названных пар от всех возможных — вторичное наблюдение: записать, порога не ставить.
